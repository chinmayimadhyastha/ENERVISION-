# ENERVISION — Frontend

**AI-powered renewable energy forecasting & decision-support for Karnataka.**

This repository contains the **frontend only** for ENERVISION: a responsive, data-focused
analytics product used to monitor solar and wind assets, inspect generation forecasts,
explore weather drivers, and review model performance.

> [!IMPORTANT]
> **Demo / illustrative data — not final research results.** The ENERVISION research
> results are **not final yet**. In the default demo mode every number comes from a
> deterministic local demo dataset and is labelled
> **`DEMO / ILLUSTRATIVE DATA — NOT FINAL RESEARCH RESULTS`** (research surfaces) or
> **`DEMO ASSET · ILLUSTRATIVE METADATA`** (plant records). Nothing here should be read as
> a validated research result or an official figure. Pointing the app at the real backend
> (see [Demo mode vs. live mode](#demo-mode-vs-live-mode)) replaces the demo layer with no
> frontend changes.

## Getting started

**Prerequisites:** Node.js 18+ (developed on Node 26) and npm.

```bash
# 1. Install dependencies
npm install

# 2. Start the dev server
npm run dev
```

Then open the printed URL (default <http://localhost:5173>).

### Production build

```bash
npm run build     # outputs to dist/
npm run preview   # serve the production build on http://localhost:4173
```

### A note for npm 12+

Recent npm versions block dependency install scripts by default. Vite relies on
`esbuild`'s postinstall step, so if `npm install` reports the script was blocked, approve
it once:

```bash
npm install-scripts approve esbuild
```

(Alternatively `npm install --foreground-scripts` / your platform's equivalent.)

## Environment variables

Copy `.env.example` to `.env` and adjust. All variables are optional.

| Variable            | Default | Purpose                                                                 |
| ------------------- | ------- | ----------------------------------------------------------------------- |
| `VITE_API_BASE_URL` | _(empty)_ | Real backend base URL, e.g. `http://localhost:5000` (the `/api` prefix is added automatically). **Empty = demo mode.** Non-empty = live HTTP. |
| `VITE_DEMO_LATENCY` | `350`   | Simulated latency (ms) for the demo layer so loading states are real.   |
| `VITE_DEBUG`        | `false` | Log each demo/live API resolution to the console.                       |

## Demo mode vs. live mode

All UI code talks to a single façade, `src/services/api.js`, and **never** imports mock
data directly. The layer resolves each call in one of two ways:

- **Demo mode (default)** — `VITE_API_BASE_URL` is empty, so responses are generated by
  `src/services/mockData.js` and wrapped in promises with simulated latency.
- **Live mode** — `VITE_API_BASE_URL` is set, so the same functions issue HTTP requests and
  the demo layer is never consulted. If a live call fails, the error is propagated to the
  caller and the page renders its **error state** (with a retry action) — the layer does
  **not** fall back to demo data, so backend and demo data are never silently mixed. The
  demo banners are hidden in this mode.

The active mode is always visible via the **Live / Demo** badge in the header and sidebar.

### Expected backend contract

The live layer calls the locked ENERVISION daily-forecasting Flask API. Every
path is relative to `VITE_API_BASE_URL` and prefixed with `/api`:

```
GET /api/health
GET /api/plants
GET /api/plants/:plant_id
GET /api/generation-history?plant_id=&type=&start_date=&end_date=
GET /api/weather?plant_id=&start_date=&end_date=
GET /api/forecast?plant_id=&model=rf|lstm|auto&horizon=1..7&base_date=
GET /api/model-performance
GET /api/feature-importance
GET /api/dashboard
GET /api/analytics?start_date=&end_date=&type=
```

The contract is **daily only**: target `DailyGeneration_MU`, unit `MU/day`.
The forecast endpoint always returns HTTP 200 with a `status` of `ok`,
`weather_required` or `insufficient_history`; `confidence` is always `null`
with a note. Feature importance uses `random_forest_impurity`
(`shap_used: false`) — it is not SHAP.

Public functions: `getDashboardData()`, `getPlants(filters)`, `getPlantById(id)`,
`getForecast(params)`, `getGenerationHistory(params)`, `getWeather(params)`,
`getAnalytics(params)`, `getModelPerformance()`, `getFeatureImportance(params)`.

## Routes

| Route                     | Page                | Highlights                                                              |
| ------------------------- | ------------------- | ----------------------------------------------------------------------- |
| `/`                       | Dashboard           | Daily fleet KPIs, observed-vs-forecast daily pulse, source split, trend, plant list, representative forecast |
| `/plants`                 | Plant Explorer      | Search + filters (type/district/sort), map + table views                |
| `/plants/:plantId`        | Plant Details       | Per-plant daily generation, observed weather, coverage and forecast capability |
| `/forecast`               | Forecast            | Plant selector (`?plant=`), model (`auto`/`rf`/`lstm`), daily horizon 1–7, honest unavailable states |
| `/analytics`              | Analytics           | Date-range switching (7/30/90/365 d), daily trend, plant comparison, explicit coverage |
| `/model-performance`      | Model Performance   | Random Forest + solar/wind LSTM, published MAE/RMSE/R² only, RF impurity importance (not SHAP) |
| `/about`                  | About ENERVISION    | Scope, architecture, objectives, data sources, disclaimer               |
| `*`                       | Not Found           | 404 fallback                                                            |

### Model Performance page

Shows only the three committed daily artifacts — **Random Forest (24 leakage-free
features, production candidate)**, **Solar LSTM** and **Wind LSTM**. MAE, RMSE and R²
are read from `/api/model-performance`; LSTMs publish only MAE, so unavailable metrics
render as “not published” and are never inferred. Feature importance is
`random_forest_impurity` (`shap_used: false`); the page never labels it SHAP. Historical
25-feature Random Forest metrics that were affected by target leakage appear only as
clearly labelled, non-comparable provenance.

## Design language

ENERVISION is presented as a *renewable-energy mission control* rather than a generic
SaaS dashboard:

- **Dark graphite foundation** with teal (`brand`), amber (`solar`) and cyan (`wind`)
  accents, thin technical borders, restrained glow and subtle grid / contour textures.
- **Karnataka is the visual identity.** The Dashboard and Plants pages are led by a real
  geographic map built from simplified district polygons (`src/data/karnatakaOutline.js`).
  Plants render as pulsing nodes whose size encodes capacity and colour encodes source;
  selecting a node opens that asset's detail view. Demo mode uses 25 illustrative assets;
  live mode renders the 37 plants returned by `/api/plants` (15 with coordinates).
- **AI forecasting is the centrepiece.** The Forecast page uses a **daily** horizon
  (`TODAY / TOMORROW / +2 … +7 DAYS`) with a day inspector showing predicted generation in
  `MU/day`, raw model output and post-processing. `confidence` is always `null` in the API,
  so the UI shows “Not calibrated” instead of a band or probability.
- **Weather → energy is made explicit.** GHI, temperature, humidity, wind speed and pressure
  are shown as observed model inputs for the selected date. Future weather is not provided
  by the backend, and historical weather is never reused as a forecast.
- **Microinteractions** — plant-node pulses, metric count-ups, chart transitions and
  active-nav transitions — all transform/opacity based and disabled under
  `prefers-reduced-motion`.

## Data & determinism

The demo dataset is generated with a **seeded PRNG** (mulberry32 + FNV hash), so every
chart, KPI and table agrees with every other and is stable across reloads. Components
never call `Math.random()`.

The demo signal follows a documented physical shape so it reads realistically:

- **Solar** — clear-sky bell curve (≈06:15–18:25) × seasonal factor × cloud attenuation × smooth noise.
- **Wind** — base capacity factor × diurnal profile × monsoon seasonality × noise.
- **Daily generation** — the hourly shape is integrated to `MU/day` so demo charts use the
  same daily contract as the backend.
- **Forecast** — an illustrative one-day daily generator (`demo_daily`). The demo layer does
  not execute the committed Random Forest or LSTM artifacts and says so in the UI.

Replacing this with real backend output is a configuration change, not a rewrite. In live
mode every page reads the API; there is no silent demo fallback.
